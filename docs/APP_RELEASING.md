# Create Desktop Release Guide

This repository builds user-facing installers in GitHub Actions and publishes them to the dedicated Cloudflare R2 bucket behind `https://download.superai.sbs`.

## Release outputs

After a tag such as `create-canvas-v0.1.21` passes all jobs, the R2 release folder contains:

- `Create-Setup-<version>-win-x64.exe`
- `Create-Setup-<version>-win-arm64.exe`
- `Create-<version>-mac-arm64.dmg`
- `Create-<version>-mac-x64.dmg`
- macOS update ZIP files
- `SHA256SUMS.txt`

Users download an installer directly. They never download server deployment archives or run shell commands.

The workflow also uploads `latest.yml`, `latest-mac.yml`, and blockmap files to the R2 update feed. GitHub Release assets are not used for installer distribution.

## Unsigned macOS fallback

If Developer ID signing and notarization credentials are not configured, tagged
releases still build an ad-hoc signed but unnotarized macOS app. This is a
temporary distribution mode for testing and early users.

Users may need to approve the app manually:

1. Open System Settings.
2. Open Privacy & Security.
3. Find the blocked Create message and choose Open Anyway.
4. Confirm the app launch.

Installed-app quarantine can also be removed explicitly:

```bash
xattr -dr com.apple.quarantine /Applications/Create.app
```

This fallback does not provide Apple identity verification. For public
distribution, configure Developer ID signing and notarization.

## macOS requirements

macOS signing and notarization require:

1. An active Apple Developer Program membership.
2. A `Developer ID Application` certificate exported as `.p12`.
3. Either an App Store Connect team API key or an Apple ID app-specific password.

The Apple Developer account and certificate cannot be generated by this repository. They must be created by the account owner.

### 1. Create the Developer ID certificate

1. Open the Apple Developer portal.
2. Open Certificates, Identifiers & Profiles.
3. Create a `Developer ID Application` certificate.
4. Create the certificate signing request with Keychain Access if requested.
5. Download and install the `.cer`.
6. Export the certificate and private key from Keychain Access as a password-protected `.p12`.
7. Record the Apple Developer Team ID.

### 2. Create notarization credentials

Recommended: App Store Connect API key.

1. Open App Store Connect.
2. Open Users and Access, then Integrations.
3. Create a Team Key with App Manager access.
4. Record the Key ID and Issuer ID.
5. Download the `.p8` file. Apple only allows downloading it once.

Alternative: create an app-specific password for the Apple ID and record the Team ID.

### 3. Add GitHub Actions secrets

Open the App repository, then Settings, Secrets and variables, Actions.

Required for tagged macOS releases:

- `CSC_LINK`: base64-encoded Developer ID Application `.p12`
- `CSC_KEY_PASSWORD`: password used when exporting the `.p12`

Use one notarization credential set:

- `APPLE_API_KEY_BASE64`: base64-encoded App Store Connect `.p8`
- `APPLE_API_KEY_ID`: App Store Connect Key ID
- `APPLE_API_ISSUER`: App Store Connect Issuer ID

or:

- `APPLE_ID`: Apple Developer account email
- `APPLE_APP_SPECIFIC_PASSWORD`: app-specific password
- `APPLE_TEAM_ID`: Apple Developer Team ID

macOS credential encoding:

```bash
base64 -i DeveloperIDApplication.p12 | pbcopy
base64 -i AuthKey_XXXXXXXXXX.p8 | pbcopy
```

PowerShell encoding alternative:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("DeveloperIDApplication.p12")) | Set-Clipboard
[Convert]::ToBase64String([IO.File]::ReadAllBytes("AuthKey_XXXXXXXXXX.p8")) | Set-Clipboard
```

### 4. Optional Windows signing

Windows code signing uses:

- `WIN_CSC_LINK`: base64-encoded `.pfx`
- `WIN_CSC_KEY_PASSWORD`: `.pfx` password

Unsigned Windows test builds can still be produced, but SmartScreen may display an unknown publisher warning.

## Publish a release

1. Commit the release changes.
2. Create and push a tag:

```bash
git tag create-canvas-v0.1.21
git push origin create-canvas-v0.1.21
```

3. The workflow builds Windows x64/ARM64 and macOS arm64/x64 packages.
4. Tagged macOS builds use Developer ID signing and notarization when credentials exist; otherwise they use the ad-hoc fallback.
5. When Developer ID credentials exist, the workflow verifies the macOS signature with `codesign`, validates the stapled notarization ticket, and runs `spctl`.
6. Installers and `SHA256SUMS.txt` are uploaded to R2 under `app-releases/v<version>/`; the four architecture-specific update manifests are uploaded under `app-releases/`; the workflow then verifies the public URLs before reporting success.

## Verify a macOS build

```bash
codesign --verify --deep --strict --verbose=2 "/Applications/Create.app"
xcrun stapler validate "/Applications/Create.app"
spctl --assess --type execute --verbose=4 "/Applications/Create.app"
```

Expected result: signature valid, notarization ticket present, and Gatekeeper assessment accepted.

## R2 download and update feed

R2 is the only public installer and updater location:

```text
app-releases/v<version>/<installer files>
app-releases/windows/x64/latest.yml
app-releases/windows/arm64/latest.yml
app-releases/macos/arm64/latest-mac.yml
app-releases/macos/x64/latest-mac.yml
```

The Web admin client-release settings must use:

```text
version: <app version>
update_base_url: https://download.superai.sbs/app-releases
windows_x64: https://download.superai.sbs/app-releases/v<version>/Create-Setup-<version>-win-x64.exe
windows_arm64: https://download.superai.sbs/app-releases/v<version>/Create-Setup-<version>-win-arm64.exe
macos_arm64: https://download.superai.sbs/app-releases/v<version>/Create-<version>-mac-arm64.dmg
macos_x64: https://download.superai.sbs/app-releases/v<version>/Create-<version>-mac-x64.dmg
```

The client version must match the App installer version, not the Web server version.
